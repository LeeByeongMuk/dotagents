# 설계: Brief 중심 제품 개발 워크플로우

- Original design: 2026-08-02
- Revised: 2026-08-10
- Status: APPROVED FOR IMPLEMENTATION
- Default path: `Brief → Execute → Verify`
- Compatibility path: `audited` ten-stage workflow

## 문제 정의

기존 제품 개발 워크플로우는 인터뷰부터 검수까지 재개 가능한 10단계 증거 사슬을 만들었다. 안전한 상태 전이와 승인 기록은 제공하지만, 일반 제품 작업에도 9~10개 산출물, 단계별 승인, 공급자 스킬 체인, 서브에이전트와 반복 검토를 기본 적용한다.

최신 모델은 전체 문맥에서 계획하고, 실행 순서와 도구를 선택하며, 결과를 검토할 수 있다. 실행 방법을 고정하는 하네스가 모델의 판단을 막고 시간·토큰·인수인계 손실을 만들 수 있다. 반면 모델은 사용자의 상황, 취향, 사업 목적과 과거 결정은 스스로 알 수 없다.

따라서 다음을 분리한다.

- **기획 하네스:** 무엇을 왜 만들지, 어떤 기준으로 결정할지 고정한다. 항상 유지한다.
- **실행 하네스:** 어떻게 계획·분할·도구 사용·검토할지 강제한다. 기본 경로에서 최소화한다.

## 목표

1. 제품 작업마다 한 개의 권위 있는 Brief 원본을 사용하고, 현재 PRD·이슈·스펙이 있으면 새 문서보다 우선한다.
2. 기본 실행은 한 주 에이전트가 전체 문맥을 유지한 채 자율적으로 수행한다.
3. 성공은 단계 통과가 아니라 수용 조건과 결정론적 검증 증거로 판정한다.
4. 규제·감사·고위험 인수인계에는 기존 10단계 계약을 계속 제공한다.
5. Claude Code, Codex, Gemini가 같은 원본을 사용한다.

## 비목표

- 외부 스킬, 멀티에이전트, RAG, 기억, 검토 기능 자체를 제거하지 않는다.
- 모든 작업을 단일 호출로 제한하지 않는다.
- 감사형 기존 실행과 상태 파일의 호환성을 깨지 않는다.
- 모델의 주관적 자체 평가만으로 테스트·보안·형식 검사를 대체하지 않는다.

## 판단 원칙

- 실행 순서 고정보다 모델 자율성을 선택한다. 현재 모델이 더 적합한 순서를 판단할 수 있기 때문이다.
- 여러 중간 문서보다 하나의 현재 Brief를 선택한다. 단계 사이 정보 손실과 충돌을 줄이기 때문이다.
- 유사한 기억보다 명시적 결정 기록을 선택한다. 관련성 오류가 답을 오염시키기 때문이다.
- 포괄적 자체 검토보다 결정론적 검증을 선택한다. 종료 조건과 성공 기준이 분명하기 때문이다.
- 역할 분리보다 문맥 연속성을 선택한다. 실제 병렬성이나 독립성이 없으면 인수인계 비용만 생기기 때문이다.
- 기본 경로 단순화보다 형식적 증거가 중요한 위험에서는 `audited`를 선택한다.

## 경로

### direct

작은 수정, 단일 버그, 설명, 조사에 사용한다. 별도 제품 Brief나 워크플로 상태를 만들지 않고 프로젝트의 일반 구현·검증 절차를 따른다.

### lean: 기본

```text
BRIEF                         EXECUTE                       VERIFY
문제·목적·판단 기준       →   계획·순서·도구를 자율 선택   →   수용 조건과 검사 증거
제약·결정 기록·수용 조건       단일 주 에이전트 문맥 유지       실패 수정과 재검증
```

현재 PRD·이슈·스펙이 제품 결정을 소유하고 계속 갱신할 수 있으면 그것을 Brief로 채택한다. 적합한 원본이 없을 때만 `docs/workflows/<run-id>/brief.md`를 만든다. 외부·읽기 전용 원본에는 링크만 두고, 로컬 Brief는 누락된 결정·체크포인트·검증 증거·위험만 기록한다.

### audited: 선택

다음 중 하나가 있을 때만 기존 10단계 계약을 사용한다.

- 사용자의 명시적 요청
- 규제나 감사에 필요한 단계별 승인 증거
- 민감한 인증·권한·결제·개인정보 경계
- 비가역 데이터 마이그레이션이나 큰 외부 부작용
- 여러 팀 사이의 공식 승인과 장기 인수인계

작업 규모와 파일 수만으로는 감사형을 선택하지 않는다.

## 필수 기획 하네스

채택한 권위 원본과 로컬 실행 기록은 합쳐서 다음을 반드시 포함한다.

1. `누가, 언제, 무엇을 하지 못해서, 무엇을 포기하는가` 형식의 문제
2. 문제가 해결되면 달라지는 결과와 성공 신호
3. `A보다 B를 선택한다. 왜냐하면 ...` 형식의 판단 원칙
4. 비용·법률·보안·일정·호환성 제약과 비목표
5. 관찰 가능한 수용 조건
6. 결정, 버린 대안, 이유와 결정자
7. 열린 제품 결정
8. 재개 체크포인트, 검증 증거와 남은 위험

사용자가 이미 제공한 정보와 저장소에서 확인 가능한 사실을 다시 질문하지 않는다. 중요한 가정·대안·사용자 소유 결정이 결과를 바꿀 수 있을 때만 실행 전에 한 묶음으로 알리고, 사용자가 결정해야 하는 정보가 방향을 막을 때만 멈춘다.

## 실행 원칙

### 프롬프트 체인

완전한 작업이 한 문맥에 들어오면 요약 → 분류 → 초안 → 검토 같은 고정 체인을 만들지 않는다. 중간 요약이 필요하면 원문과 함께 사용하고, 요약만 다음 단계에 전달하지 않는다.

### 규칙

팀 고유 기준, 권한, 보안, 비밀, 검증 정책은 유지한다. 과거 모델의 형식 실수나 도구 선택을 보정하기 위한 규칙은 반복되는 현재 증거가 없으면 추가하지 않는다.

### 멀티에이전트

다음에만 사용한다.

- 독립 작업의 실제 병렬 실행
- 문맥 격리나 전문 도구가 필요함
- 고위험 판단의 독립적 두 번째 의견

기획자·작성자·검토자 역할만 나누는 구조는 기본 금지다.

### 검토 루프

문제가 없어도 흠을 찾게 하는 반복 검토나 고정된 모델 자기검토 패스를 사용하지 않는다. 수용 조건, 테스트, 형식, 계산, 보안 경계처럼 구체적 기준을 검증하고, diff나 위험이 정당화할 때만 표적 검토한다. 변경이 생기면 영향받은 기준만 다시 검증한다.

### 모델별 검증

결정론적 프로젝트 검사는 모델과 무관하게 유지한다. 모델이 생성하는 자기검토와 검증 위임만 다음처럼 구분한다.

- GPT-5.6 Sol: 프롬프트를 간결하게 유지하고 구체적 diff 위험이 없는 일반 자기검토를 추가하지 않는다.
- Claude Opus 5: 모델이 기본으로 수행하는 자기수정을 중복하는 최종 재검토나 검증 서브에이전트를 추가하지 않는다.
- Claude Fable 5: 짧은 작업에는 추가 검증 하네스를 두지 않는다. 장기 실행에서는 도구 결과로 진행 주장을 확인하고, 결과를 바꿀 수 있는 스펙·위험 체크포인트에만 fresh-context 검증자를 사용할 수 있다.
- 모델이 갱신되면 현재 하네스와 축소 하네스를 대표 작업에서 비교하고, 측정된 이득이 없는 모델 전용 지시는 제거한다.

### 외부 프레임워크와 스킬

설치 여부만으로 호출하지 않는다. 현재 작업에 필요한 특화 능력과 추가되는 문맥·게이트 비용을 비교한다. 공급자 실패를 고치기 위해 사용자 작업을 중단하지 않고 내장 절차로 돌아간다.

### 기억과 검색

유사도 기반 과거 대화를 자동 주입하지 않는다. Brief와 명시적 프로젝트 결정만 기본 기억으로 사용한다. 문서 전체가 문맥에 들어오면 전체를 우선하고, 너무 큰 자료에만 검색·RAG를 사용하며 원칙과 예외의 연결을 복원한다.

### 도구 사용

“최신이라는 단어가 있으면 검색” 같은 키워드 규칙을 만들지 않는다. 최신성, 계산, 외부 상태, 불확실성, 부작용을 기준으로 모델이 도구를 선택한다.

## 검증 경계

다음은 계속 강제한다.

- 프로젝트가 정한 테스트·정적 검사·빌드
- 스키마, 형식, 필수 항목, 계산 결과
- 보안·권한·데이터 무결성
- 비가역 행동과 외부 상태 변경 전 사용자 권한
- 변경 후 실제 명령 결과와 실패 공개

검증 도구의 통과가 제품 품질 전체를 보장한다고 표현하지 않는다. 각 증거가 무엇을 증명하는지 Brief에 분리해 기록한다.

## 호환성과 전환

- 기존 `workflow.toml`, `workflow.sh`, 상태 버전 1과 10단계 테스트를 유지한다.
- 해당 CLI는 `audited` 경로에서만 사용한다는 설명을 추가한다.
- 기본 스킬은 lean 경로에서 감사형 reference와 machine contract를 읽지 않는다.
- 기존 단계 공급자는 감사형 슬롯으로 계속 등록한다.
- 기존 audited 상태 머신의 상세 잠금·해시·복구 설계는 최초 구현 커밋 `f18ca30`의 이 문서 이력과 현재 회귀 테스트에서 추적한다.
- 실제 사용 후 시간, 토큰, 사용자 중단 횟수, 결함, 재개 성공률을 모델별로 비교해 추가 단순화를 결정한다.
- audited 단계 수와 상태 버전은 실제 사용·감사 요구 증거 없이 줄이지 않는다. 사용되지 않거나 더 작은 승인 계약으로 같은 증거를 만들 수 있음이 확인되면 별도 호환 변경으로 축소한다.

## 성공 기준

- 스킬 설명과 사용서에서 `Brief → Execute → Verify`가 기본 경로다.
- Brief reference가 기존 권위 원본 재사용과 로컬 fallback을 구분하고 문제·결과·판단 기준·제약·결정 기록을 필수로 검증한다.
- 감사형 CLI와 기존 회귀 테스트가 계속 통과한다.
- 구조 테스트가 lean 기본값과 audited 호환 경로를 모두 확인한다.
- README와 레지스트리가 같은 라우팅을 설명한다.
