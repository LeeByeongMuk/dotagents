## 문제 정의

dotagents에는 공통 규칙, 스킬, 훅, 외부 연동과 도구별 어댑터를 담을 구조는 있지만, 사용자가 이미지로 정의한 제품 개발 절차를 실제 프로젝트에서 시작하고 중단 후 재개하며 완료 여부까지 검증할 실행 기능은 없다. 목표는 다음 10단계를 Claude Code, Codex, Gemini에서 공통으로 재사용할 수 있는 워크플로우로 만드는 것이다.

1. 그릴미 인터뷰
2. 도메인 파일 작성
3. gstack office hours
4. 라이트 스펙
5. 플랜
6. 플랜 리뷰 검수
7. 서브에이전트 코드
8. 코드·테스트 리뷰
9. 아키텍처 개선
10. 스킬 리팩터링(선택)

워크플로우는 외부 스킬을 무조건 복제하거나 특정 호스트의 명령 문법에 종속되지 않아야 한다. 설치된 외부 스킬이 있으면 활용하고, 없으면 동일한 산출물 계약을 만족하는 내장 절차로 계속 진행해야 한다.

## 무엇이 좋은가

이 기능의 핵심은 좋은 프롬프트를 모아 놓는 것이 아니라, 아이디어에서 검증 증거가 기록된 구현까지 이어지는 작업의 상태를 프로젝트 안에 남기는 것이다. 어떤 호스트를 사용하더라도 각 단계가 관련된 승인 산출물의 사슬을 입력으로 받으므로, 세션이나 에이전트가 바뀌어도 같은 지점에서 이어갈 수 있다.

## 제약

- 사람이 편집하는 원본은 기존 원칙대로 `agents/` 아래에 둔다.
- 루트에는 새 `skills/`, `hooks/`, `workflows/` 디렉터리를 만들지 않는다.
- 사람용 문서와 단계별 실행 산출물은 한국어 단일본으로 관리한다.
- `SKILL.md`, `AGENTS.md`, TOML과 런타임 상태처럼 에이전트·기계가 직접 소비하는 파일도 단일 원본으로 유지한다.
- 비밀, 절대 저장소 경로, 특정 프로젝트의 비공개 정보는 기록하지 않는다.
- 외부 스킬은 선택 의존성이다. 미설치 상태에서도 워크플로우가 막히지 않아야 한다.
- 현재 범위는 로컬 실행과 검증까지다. 외부 스킬 자동 다운로드, MCP 자격 증명 설정, 자동 배포는 포함하지 않는다.
- 런타임 상태는 공유 원본인 `.agents` 안에 쓰지 않는다.

## 전제 검토

### 전제 1: 10단계 모두를 항상 실행해야 한다

그렇지 않다. 이미지의 순서는 의미 있는 제품 개발 작업의 기본 경로다. 오케스트레이터가 시작 전에 작업을 다음 기준으로 분류하고 사용자에게 적용 여부를 확인한다.

- `small`: 요구가 확정된 단일 파일·국소 변경이며 제품·도메인 결정이 없음. 이 워크플로우를 시작하지 않는다.
- `standard`: 새 사용자 동작이나 아직 결정되지 않은 요구가 있지만 하나의 경계 안에서 끝남. 10단계 계약을 사용한다.
- `substantial`: 여러 화면·서비스·도메인 경계를 건드리거나 아키텍처 결정이 필요함. 10단계 계약과 더 강한 플랜 리뷰를 사용한다.

CLI는 `standard`와 `substantial`만 허용하며 `--scope`와 상태에 분류를 기록한다. 10단계는 시작할 때 선택적으로 제외할 수 있다.

### 전제 2: 외부 스킬 이름이 곧 워크플로우 계약이다

그렇지 않다. `grilling`, gstack, Superpowers는 구현 공급자다. 워크플로우 계약은 단계별 입력, 산출물, 승인 조건이다. 공급자의 이름이나 설치 경로가 바뀌어도 계약은 유지되어야 한다.

### 전제 3: Markdown만 있으면 재개와 완료 검증이 가능하다

불충분하다. 문서는 사람이 읽기 좋지만 현재 단계, 승인 여부, 산출물 누락을 안정적으로 판별하기 어렵다. 최소 상태 도구가 필요하다.

### 전제 4: 완전한 워크플로우 엔진이 필요하다

과하다. AI가 내용과 판단을 만들고, 결정론적 도구는 상태 전이와 파일 존재만 검증하면 된다. 셸 기반의 작은 상태 관리기로 충분하다.

## 검토한 접근

### 접근 A: 선언형 계약 + 오케스트레이터 스킬 + 작은 상태 도구

`workflow.toml`에 단계를 선언하고, 공통 `SKILL.md`가 실행 규칙을 제공하며, 작은 CLI가 시작·상태·승인·완료 검증을 담당한다. 호스트별 설치는 같은 스킬 원본을 링크한다.

- 장점: 호스트 중립, 재개 가능, 테스트 가능, 외부 스킬 교체 가능
- 비용: 상태 포맷과 CLI를 설계하고 설치 테스트를 확장해야 함

### 접근 B: Markdown 플레이북만 제공

한 문서에 10단계와 프롬프트를 적고 사용자가 수동으로 진행한다.

- 장점: 구현이 가장 작음
- 단점: 재개, 승인 게이트, 누락 검증, 호스트 설치를 자동화하지 못함

### 접근 C: 완전한 CLI 상태 머신

CLI가 단계 실행과 외부 도구 호출까지 모두 통제한다.

- 장점: 높은 자동화
- 단점: 호스트별 호출 방식과 외부 스킬 버전에 강하게 결합하고 유지보수 범위가 커짐

## 권장 접근

접근 A를 선택한다. 워크플로우 의미는 선언형 계약에, 대화와 판단은 오케스트레이터 스킬에, 기계적으로 판별할 상태는 CLI에 분리한다. 이 구분은 dotagents를 자산 모음이 아니라 여러 프로젝트에서 재사용 가능한 최종 운영 셋업으로 만드는 데 필요한 최소 경계다.

## 설계

### 원본과 설치 구조

```text
agents/workflows/product-development/
├── WORKFLOW.md                     # 한국어 사용법
└── workflow.toml                   # 단계·산출물·승인 계약

agents/skills/owned/product-development-workflow/
├── SKILL.md                        # 호스트 중립 오케스트레이터
├── agents/openai.yaml              # Codex UI 메타데이터
└── references/
    ├── stages.md                   # 단계별 실행 규칙
    └── artifacts.md                # 산출물 내용 계약

tooling/scripts/workflow.sh         # 결정론적 상태 도구
tooling/tests/workflow_test.sh      # 상태 전이·실패·재개 테스트
```

호스트별 발견 경로는 2026-08-02의 공식 규격과 로컬 설치를 기준으로 다음처럼 고정한다.

| 호스트 | 사용자 범위 | 프로젝트 범위 | 제공 방법 |
|---|---|---|---|
| Claude Code | `~/.claude/skills/<name>` | `.claude/skills/<name>` | 설치 매니페스트가 원본 스킬 링크를 생성 |
| Codex | `~/.agents/skills/<name>` | `.agents/skills/<name>` | 기존 `.agents` 링크와 `agents/skills/<name>` 발견용 별칭으로 제공 |
| Gemini CLI | `~/.agents/skills/<name>` 또는 `~/.gemini/skills/<name>` | `.agents/skills/<name>` 또는 `.gemini/skills/<name>` | Codex와 같은 `.agents` 별칭을 사용 |

스킬 원본은 항상 `agents/skills/owned/product-development-workflow/`에 있고 `agents/skills/product-development-workflow`는 발견을 위한 상대 심볼릭 링크일 뿐이다. 공통 CLI는 프로젝트 설치에서 `<project>/.dotagents/bin/dotagents-workflow`, 전역 설치에서 `~/.local/bin/dotagents-workflow`로 연결한다. 전역 설치 시 `~/.local/bin`이 `PATH`에 없으면 설치는 성공하되 실행 가능한 경고와 직접 경로를 출력한다.

### 런타임 저장 위치

대상 프로젝트의 로컬 실행 상태는 다음 위치에 둔다.

```text
<project>/.dotagents/runs/<run-id>/state
<project>/docs/workflows/<run-id>/
├── 01-interview.md
├── ...
└── 10-skill-retro.md
```

`.dotagents/runs/`는 로컬 상태다. Git 저장소에서는 `--project`가 `git rev-parse --show-toplevel`의 물리 경로와 같아야 하며, 다르면 올바른 프로젝트 루트를 안내하고 중단한다. `start`는 `git rev-parse --git-path info/exclude`가 가리키는 로컬 exclude 파일에 `/.dotagents/runs/`를 한 번만 추가하며, 저장소의 `.gitignore`는 바꾸지 않는다. `docs/workflows/`의 산출물은 팀이 검토하고 이어갈 수 있도록 커밋 가능한 문서다. `run-id`는 소문자 영숫자와 하이픈만 허용하여 경로 이탈을 막는다.

### 상태 모델

상태 파일은 셸에서 안전하게 읽을 수 있도록 실행 가능한 코드가 아닌 `key=value`의 제한된 형식으로 쓴다. 고정된 키 27개만 한 번씩 허용하고 값은 허용 목록·숫자·UTC 시각·SHA-256으로 제한하며 파일 전체를 `source`하지 않는다. 이 파일 하나만 실행 상태와 승인 기록의 권위 있는 원본이다.

- `state_version`: 상태 포맷 버전
- `run_id`: 검증된 실행 ID
- `scope`: `standard`, `substantial`
- `current_stage`: 다음에 실행할 단계 번호
- `approved_through`: 사용자가 승인한 마지막 단계
- `status`: `active`, `completed`
- `optional_skill_refactor`: `yes`, `no`
- `approval_01_at` ... `approval_10_at`: 승인 전에는 `-`, 이후에는 `YYYY-MM-DDTHH:MM:SSZ`
- `artifact_01_sha256` ... `artifact_10_sha256`: 승인 전에는 `-`, 이후에는 사용자가 승인한 정확한 파일의 SHA-256

명령은 다음으로 제한한다.

```text
dotagents-workflow start --project PATH --run RUN_ID --scope standard|substantial [--skip-skill-refactor]
dotagents-workflow status --project PATH --run RUN_ID
dotagents-workflow approve --project PATH --run RUN_ID --stage N --user-approved
dotagents-workflow adopt --project PATH --run RUN_ID --scope standard|substantial --through N --user-approved [--skip-skill-refactor]
dotagents-workflow verify --project PATH --run RUN_ID
```

`start`는 실행 디렉터리와 상태를 생성한 뒤 `status`와 같은 10단계 목록을 출력하되 산출물 내용을 만들지 않는다. `approve`는 오케스트레이터가 실제 사용자에게 명시적 승인을 받은 뒤에만 `--user-approved`와 함께 호출한다. CLI는 현재 단계의 한국어 산출물이 존재하고 비어 있지 않은 일반 파일이며 심볼릭 링크가 아니고 정규 산출물 디렉터리 바로 아래에 있는지 구조적으로 확인한 뒤, 단일 상태 파일에 승인 UTC 시각과 파일의 SHA-256을 기록한다. 이후 `status`, 다음 `approve`, `verify`는 승인된 모든 산출물의 해시를 다시 확인하여 변경된 승인 증거를 거부한다. 산출물 품질은 오케스트레이터와 사용자가 검토하며 CLI가 보증한다고 표현하지 않는다.

`adopt`는 기존 인터뷰·스펙·플랜을 정해진 파일 이름으로 **복사한** 뒤 사용하는 복구·가져오기 명령이다. 외부 또는 심볼릭 링크는 이동성과 경로 안전 때문에 허용하지 않는다. `N`은 1~10이며 1단계부터 `N`단계까지 모든 산출물이 일반 파일로 있고 사용자가 전체를 승인한 경우에만 새 상태와 승인 해시를 만든다. `N < 9`이면 `current_stage=N+1`, `approved_through=N`, `active`다. `N=9`는 10단계가 켜져 있으면 `current_stage=10`, `approved_through=9`, `active`이고, 10단계를 생략한 실행이면 같은 숫자와 `completed`다. `N=10`은 10단계가 켜져 있을 때만 허용하며 `current_stage=10`, `approved_through=10`, `completed`다. `--through 10 --skip-skill-refactor`는 거부한다. 상태 없이 산출물 디렉터리만 존재하거나 상태 파일만 사라진 빈 실행 상태 디렉터리가 남으면 `start`는 실패하고 `adopt`로 복구할 수 있다. 실제 상태 파일이나 다른 런타임 파일이 남은 디렉터리는 덮어쓰지 않는다.

`verify`는 필수 단계의 산출물이 정규 디렉터리 아래의 일반 비심볼릭 링크 파일인지, 승인 시각과 SHA-256이 연속되는지, 현재 파일이 승인된 해시와 같은지, 완료 상태가 맞는지를 점검하는 **워크플로우 구조·무결성 검증**이다. 구현이 정확하거나 테스트가 성공했다고 독립적으로 증명하지는 않는다. 그 증거는 7~9단계 산출물의 필수 항목과 사용자 승인에 남는다.

### 선언형 계약 스키마

`workflow.toml`은 일반 TOML 전체가 아니라 의존성 없이 안전하게 파싱하기 위한 제한된 줄 단위 프로필이다. 최상위에는 `schema_version`, `id`, `state_version`을 한 번씩 두고, 각 `[[stages]]` 블록에는 다음 키를 정확히 이 순서로 한 번씩 둔다.

```toml
schema_version = 1
id = "product-development"
state_version = 1

[[stages]]
number = 1
id = "interview"
title_ko = "그릴미 인터뷰"
artifact = "01-interview"
optional = false
predecessor = 0
requires_approval = true
```

문자열은 큰따옴표로 감싼 ASCII ID·파일 기본 이름 또는 UTF-8 제목만, `optional`은 `true|false`, 숫자는 0~10만 허용한다. 버전 1에서는 `requires_approval`이 모든 단계에서 반드시 `true`여야 한다. 단계는 1부터 10까지 연속이고 `predecessor = number - 1`이어야 하며 선택 단계는 10 하나뿐이다. `workflow.sh`의 `awk` 파서는 이 제한 프로필을 TSV로 변환하고 알 수 없는 키·순서·중복·버전을 거부한다. `status`, `approve`, `adopt`, `verify`와 테스트는 이 TSV에서 단계 이름·산출물·선택 여부를 읽으므로 셸에 별도 단계 표를 중복하지 않는다.

### 상태 불변조건과 전이

- 활성 상태는 `current_stage = approved_through + 1`, `status = active`를 만족한다.
- 최초 상태는 `current_stage = 1`, `approved_through = 0`, 모든 승인 시각과 산출물 해시가 `-`다.
- 현재 단계만 승인할 수 있고 재승인·역순 승인·임의 건너뛰기는 실패한다.
- 10단계를 사용하는 실행은 10단계 승인 뒤 `current_stage = 10`, `approved_through = 10`, `status = completed`다.
- 10단계를 제외한 실행은 9단계 승인 뒤 `current_stage = 10`, `approved_through = 9`, `status = completed`다.
- 완료 상태에는 추가 승인을 허용하지 않는다.
- 상태 버전이 지원 범위와 다르면 변경하지 않고 업그레이드가 필요하다는 오류로 종료한다.
- 변경 명령은 먼저 상태 루트의 임시 owner 파일에 `pid=<숫자>`, `created_at=<Unix epoch>`, `process_started=<ps -p PID -o lstart= 값>`, `token=<임의 토큰>` 네 줄을 완전히 쓴다. 그 다음 `.dotagents/runs/.<run-id>.lock` 디렉터리를 `mkdir`로 원자적으로 획득하고, 완성된 owner 파일을 덮어쓰지 않는 하드 링크로 게시한다. 경쟁 프로세스는 `owner`가 없고 디렉터리 생성 후 5초 이내면 초기화 중인 살아 있는 잠금으로 보고 회수하지 않으며, 5초가 지난 소유자 없는 잠금만 오래된 것으로 본다. 오래된 잠금은 고유 격리 경로로 원자 이동한 뒤 제거한다. 원래 프로세스가 회수 뒤 재개되어도 이미 게시된 새 owner를 덮어쓸 수 없다. 정상·신호 종료, 상태 쓰기 직전과 해제 시에는 owner 토큰이 현재 명령과 같은지 다시 확인한다. 소유권은 `kill -0 PID` 성공과 가능한 경우 현재 `ps` 시작 시각이 기록값과 같은지를 함께 비교하여 Bash 프로세스 이름 문제와 PID 재사용을 피한다. 샌드박스처럼 `ps`가 금지되어 `process_started=unavailable`이면 살아 있는 PID를 시간만으로 회수하지 않고 실패 폐쇄한다. 소유자 없는 초기화 구간, 죽은 소유자, PID 재사용 형태, 오래 실행 중인 소유자와 실제 동시 승인을 테스트한다.
- 상태 변경은 같은 디렉터리의 임시 파일을 완전히 쓴 뒤 `mv`로 단일 권위 파일을 원자적으로 교체한다. 읽기 명령은 잠금이 살아 있으면 변경 중이라고 실패하고, 오래된 잠금이면 회수한 뒤 상태를 읽는다. 승인된 산출물은 불변 증거이며 해시가 달라지면 읽기와 후속 변경 모두 실패한다.
- 프로젝트 루트를 물리 경로로 정규화하고 상태·산출물 루트 또는 실행 디렉터리가 심볼릭 링크면 중단한다.
- 성공은 종료 코드 0, 사용법·입력 오류는 2, 상태/계약/산출물 검증 실패는 3으로 구분하며 사람용 `key: value` 출력을 사용한다.

### 단계 계약

| 단계 | 기본 실행 방식 | 승인 산출물 |
|---|---|---|
| 1. 인터뷰 | `grilling`/`grill-me`가 있으면 사용, 아니면 한 번에 한 질문씩 내장 인터뷰 | `01-interview.md` |
| 2. 도메인 | 액터, 용어, 엔터티, 명령·이벤트, 불변조건, 경계, 비목표 정리 | `02-domain.md` |
| 3. Office hours | gstack `office-hours`가 있으면 사용, 아니면 전제 반박과 2~3개 접근 비교 | `03-design.md` |
| 4. 라이트 스펙 | 목표, 비목표, 사용자 이야기, 수용 조건, 제약, 열린 질문 | `04-spec.md` |
| 5. 플랜 | Superpowers `writing-plans` 우선, 정확한 파일·작업·테스트 명령 포함 | `05-plan.md` |
| 6. 플랜 리뷰 | gstack `autoplan` 또는 CEO·디자인·엔지니어링 리뷰 조합 | `06-plan-review.md` |
| 7. 구현 | 가능하면 작업별 새 서브에이전트, TDD, 명세 준수 후 품질 검토 | `07-implementation.md` |
| 8. 코드·테스트 리뷰 | 프로젝트 검사, 코드 리뷰, 제품 종류에 맞는 QA 후 재검증 | `08-review.md` |
| 9. 아키텍처 평가·개선 | 결합도·응집도·중복·경계를 평가하고, 사용자 승인과 근거가 있을 때만 변경한 뒤 8단계 검사를 모두 재실행 | `09-architecture.md` |
| 10. 스킬 리팩터링 후보 | 반복 성공한 절차와 스킬 후보를 보고하며, 별도 쓰기 승인이 있을 때만 스킬 생성; 시작 시 생략 가능 | `10-skill-retro.md` |

각 단계는 바로 전 문서만이 아니라 판단에 필요한 모든 승인된 앞 단계 산출물을 입력으로 사용한다. 특히 7단계 구현은 `04-spec`, `05-plan`, `06-plan-review`를 모두 읽고 충돌이 있으면 가장 최근 사용자 승인 결정을 따른다. 에이전트는 사실을 저장소나 공식 문서에서 확인할 수 있으면 사용자에게 묻지 않고 조사한다. 제품 결정은 추정하지 않고 사용자 승인을 받는다. `artifacts.md`는 단계마다 목적·입력·결정·열린 질문을 요구하고, 7~9단계에는 변경 파일, 실행 명령, 종료 결과, 남은 실패, 사용자 결정을 필수로 요구한다. 9단계 변경이 있으면 8단계의 모든 관련 검사를 다시 실행한 결과 없이는 승인할 수 없다.

### 실패와 복구

- 외부 스킬 미설치: 내장 실행 규칙으로 계속한다.
- 외부 스킬이 설치되었지만 실패하거나 계약과 호환되지 않음: 실패 원인을 현재 산출물에 기록하고 내장 절차로 한 번 재시도한다. 외부 스킬을 자동 수정·다운그레이드하지 않는다.
- 산출물 누락/빈 파일: `approve`가 실패하고 누락 파일을 표시한다.
- 상태 파일 손상/알 수 없는 키: 상태를 실행하지 않고 검증 오류로 중단한다.
- 중단된 세션: `status`로 현재 단계와 필요한 파일을 확인하고 같은 단계에서 재개한다. 상태 파일을 잃고 산출물과 빈 실행 상태 디렉터리만 남았으면 사용자가 검토한 뒤 `adopt`로 복구한다.
- 설치된 링크의 원본 이동: 기존 설치기 규칙대로 매니페스트가 소유한 링크만 재설치로 복구한다.
- 기존 사용자 파일 충돌: 기본 설치는 전혀 변경하지 않고 중단하며 `--force`에서만 백업한다.

### 라우팅

사용자가 “제품을 처음부터 만들자”, “아이디어를 인터뷰부터 구현까지 진행하자”, 또는 이 10단계 워크플로우를 명시하면 오케스트레이터를 사용한다. 단일 버그, 작은 수정, 설명·조사 요청에는 사용하지 않는다. 기존 스펙이나 플랜부터 시작할 때는 문서를 정규 산출물 이름의 일반 파일로 복사하고, 빠진 앞 단계는 기존 문서에서 필요한 내용을 보완한 뒤 사용자가 묶음으로 확인하면 `adopt --through N --user-approved`로 가져온다. 인터뷰를 형식적으로 다시 실행하거나 빈 자리표시자를 승인하지 않는다.

### 문서 언어 정책

초기 설계에서는 한·영 문서 쌍을 고려했으나, 2026-08-03 사용자 결정에 따라 저장소 문서와 대상 프로젝트의 실행 산출물을 한국어 단일본으로 관리한다. 구조 테스트는 중복 `.en.md` 문서가 다시 추가되지 않는지 검사한다. 에이전트 지시와 기계 계약도 단일 원본을 유지한다.

## 열린 질문

- 자동 배포·PR 생성을 11번째 단계로 만들지 여부는 실제 사용 기록을 본 뒤 결정한다. 현재는 10단계 완료 후 선택 가능한 다음 행동으로 안내한다.
- 서로 다른 `run-id`는 상태만 분리한다. 같은 작업 트리에서 구현을 병렬 실행하면 충돌할 수 있으므로 각 실행은 별도 브랜치·worktree를 사용해야 한다.

## 성공 조건

- 새 프로젝트에서 한 명령으로 워크플로우를 시작하고, 같은 출력에서 10단계와 필요한 산출물을 확인할 수 있다.
- 산출물이 없으면 단계를 승인할 수 없고, 중단 후 같은 상태에서 재개할 수 있다.
- 외부 스킬이 하나도 없어도 오케스트레이터의 내장 절차로 모든 단계를 수행할 수 있다.
- 전역·프로젝트 설치가 세 호스트의 스킬 경로를 만들고 반복 설치·저장소 이동·제거 테스트를 통과한다.
- 한국어 단일 문서와 실제 프로젝트 적용 예시가 제공된다.
- `./tooling/scripts/check.sh`, 설치 테스트, 구조 테스트, 워크플로우 테스트가 모두 통과한다.

## 배포 방식

기존 dotagents 설치기의 전역·프로젝트 심볼릭 링크 설치로 배포한다. 별도 패키지 매니저나 네트워크 다운로드는 추가하지 않는다. GitHub PR에서 전체 검사 결과를 확인하고 머지한 뒤 사용자는 저장소를 pull하고 설치기를 다시 실행한다.

## 검수 기록

## 당신의 사고에서 관찰한 점
