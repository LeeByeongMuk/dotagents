# 설계: Brief 중심 제품 개발 워크플로우

- Original design: 2026-08-02
- Revised: 2026-09-30
- Status: IMPLEMENTED
- Planning path: `Plan`
- Implementation path: `Brief → Execute → Verify`

## 문제 정의

기존 제품 개발 워크플로우는 인터뷰부터 검수까지 재개 가능한 10단계 증거 사슬을 만들었다. 안전한 상태 전이와 승인 기록은 제공하지만, 일반 제품 작업에도 9~10개 산출물, 단계별 승인, 공급자 스킬 체인, 서브에이전트와 반복 검토를 기본 적용했다.

최신 모델은 전체 문맥에서 계획하고, 실행 순서와 도구를 선택하며, 결과를 검토할 수 있다. 실행 방법을 고정하는 하네스가 모델의 판단을 막고 시간·토큰·인수인계 손실을 만들 수 있다. 반면 기획 요청과 구현 요청을 같은 경로로 처리하면 사용자가 승인하지 않은 변경으로 넘어갈 수 있고, Codex와 Claude Code의 검증 차이를 한 지침에 모두 넣으면 각 호스트가 불필요한 문맥을 읽는다.

따라서 다음을 분리한다.

- **기획 하네스:** 무엇을 왜 만들지, 어떤 기준으로 결정할지 고정한다. 항상 유지한다.
- **실행 하네스:** 어떻게 계획·분할·도구 사용·검토할지 강제한다. 기본 경로에서 최소화한다.

## 목표

1. 제품 작업마다 한 개의 권위 있는 Brief 원본을 사용하고, 현재 PRD·이슈·스펙이 있으면 새 문서보다 우선한다.
2. 기본 실행은 한 주 에이전트가 전체 문맥을 유지한 채 자율적으로 수행한다.
3. 성공은 단계 통과가 아니라 수용 조건과 결정론적 검증 증거로 판정한다.
4. 규제·감사·고위험 작업도 별도 상태 머신 없이 lean에서 필요한 승인과 증거를 수용 조건으로 다룬다.
5. Claude Code, Codex, Gemini가 같은 원본을 사용한다.
6. 기획 요청은 구현 없이 끝나고, 사용자가 구현을 요청한 경우에만 실행 경로로 넘어간다.
7. Claude Code와 Codex는 같은 결과 계약을 사용하되 호스트별 검증 지침은 서로 로드하지 않는다.
8. 사용자가 요청하면 작업 성공 가능성, 문맥 연속성, 비용과 지연을 근거로 실행 모델을 권고한다.

## 비목표

- 외부 스킬, 멀티에이전트, RAG, 기억, 검토 기능 자체를 제거하지 않는다.
- 모든 작업을 단일 호출로 제한하지 않는다.
- 모델의 주관적 자체 평가만으로 테스트·보안·형식 검사를 대체하지 않는다.
- Claude Code나 Codex 호스트 자체의 모델 전환 API를 구현하지 않는다.
- 모델 카탈로그와 가격표를 저장소 안에 고정하지 않는다.

## 판단 원칙

- 실행 순서 고정보다 모델 자율성을 선택한다. 현재 모델이 더 적합한 순서를 판단할 수 있기 때문이다.
- 여러 중간 문서보다 하나의 현재 Brief를 선택한다. 단계 사이 정보 손실과 충돌을 줄이기 때문이다.
- 유사한 기억보다 명시적 결정 기록을 선택한다. 관련성 오류가 답을 오염시키기 때문이다.
- 포괄적 자체 검토보다 결정론적 검증을 선택한다. 종료 조건과 성공 기준이 분명하기 때문이다.
- 역할 분리보다 문맥 연속성을 선택한다. 실제 병렬성이나 독립성이 없으면 인수인계 비용만 생기기 때문이다.
- 별도 감사 상태 머신보다 lean 수용 조건 안의 승인·증거를 선택한다. 쓰이지 않는 10단계 계약의 유지 비용이 그 이득보다 컸기 때문이다(ADR 0005).
- 추정상 더 강한 모델보다 현재 문맥을 기본값으로 선택한다. 하드 제약이나 대표 eval처럼 이전 비용을 상쇄하는 근거가 있을 때만 전환하기 때문이다.
- 공급자별 고정 표보다 공통 후보 계약을 선택한다. Claude·Codex를 먼저 지원하면서 로컬 LLM을 같은 인터페이스로 확장할 수 있기 때문이다.

## 경로

### direct

작은 수정, 단일 버그, 설명과 제품 결정을 만들지 않는 사실 조사에 사용한다. 별도 제품 Brief나 워크플로 상태를 만들지 않고 프로젝트의 일반 절차를 따른다.

### plan: 기획 전용

제품 문제 탐색, 대안 비교, 기획, 설계 요청에 사용한다. 저장소와 현재 제품 원본을 조사하고 문제, 결과·성공 신호, 판단 원칙, 제약·비목표, `AC-<번호>` 수용 조건, 결정·버린 대안, 열린 결정을 반환한다. 사용자가 문서 수정을 요청하지 않았다면 파일을 만들지 않으며 구현과 구현 검증으로 넘어가지 않는다. “조사”나 “탐색”은 제품 결정을 만들 때만 이 경로이며 기존 사실 설명은 `direct`다.

기획과 구현이 함께 명시되면 구현 권한을 우선해 `lean`을 선택한다. 고위험 주제만 제시된 기획 요청은 구현 권한으로 확대하지 않는다.

### lean: 기본

```text
BRIEF                    MODEL FIT(요청 시)             EXECUTE                    VERIFY
문제·목적·판단 기준   →   후보·제약·eval 비교       →   계획·순서·도구를 자율 선택   →   수용 조건과 검사 증거
제약·결정·수용 조건       유지·전환 권고와 근거 기록       단일 주 에이전트 문맥 유지       실패 수정과 재검증
```

현재 PRD·이슈·스펙이 제품 결정을 소유하고 계속 갱신할 수 있으면 그것을 Brief로 채택하고 fallback 템플릿을 읽지 않는다. 적합한 원본이 없거나 외부·읽기 전용 원본에 실행 기록을 보완해야 할 때만 `references/brief-template.md`를 읽고 `docs/workflows/<run-id>/brief.md`를 만든다.

규제, 민감한 인증·권한·결제·개인정보 경계, 비가역 데이터 변경, 여러 팀의 공식 승인처럼 형식적 증거가 필요한 작업도 lean으로 진행하고, 필요한 승인과 증거를 Brief의 수용 조건으로 둔다.

## 필수 기획 하네스

채택한 권위 원본과 로컬 실행 기록은 합쳐서 다음을 반드시 포함한다.

1. `누가, 언제, 무엇을 하지 못해서, 무엇을 포기하는가` 형식의 문제
2. 문제가 해결되면 달라지는 결과와 성공 신호
3. `A보다 B를 선택한다. 왜냐하면 ...` 형식의 판단 원칙
4. 비용·법률·보안·일정·호환성 제약과 비목표
5. 안정적인 `AC-<번호>`가 붙은 관찰 가능한 수용 조건
6. 결정, 버린 대안, 이유와 결정자
7. 열린 제품 결정
8. 재개 체크포인트, 검증 증거와 남은 위험

사용자가 이미 제공한 정보와 저장소에서 확인 가능한 사실을 다시 질문하지 않는다. 중요한 가정·대안·사용자 소유 결정이 결과를 바꿀 수 있을 때만 실행 전에 한 묶음으로 알리고, 사용자가 결정해야 하는 정보가 방향을 막을 때만 멈춘다.

## 실행 원칙

### 프롬프트 체인

완전한 작업이 한 문맥에 들어오면 요약 → 분류 → 초안 → 검토 같은 고정 체인을 만들지 않는다. 중간 요약이 필요하면 원문과 함께 사용하고, 요약만 다음 단계에 전달하지 않는다.

### 규칙

팀 고유 기준, 권한, 보안, 비밀, 검증 정책은 유지한다. 과거 모델의 형식 실수나 도구 선택을 보정하기 위한 규칙은 반복되는 현재 증거가 없으면 추가하지 않는다.

### 멀티에이전트

다음에만 사용한다.

- 독립 작업의 실제 병렬 실행
- 문맥 격리나 전문 도구가 필요함
- 고위험 판단의 독립적 두 번째 의견

기획자·작성자·검토자 역할만 나누는 구조는 기본 금지다.

### 검토 루프

문제가 없어도 흠을 찾게 하는 반복 검토나 고정된 모델 자기검토 패스를 사용하지 않는다. 수용 조건, 테스트, 형식, 계산, 보안 경계처럼 구체적 기준을 검증하고, diff나 위험이 정당화할 때만 표적 검토한다. 변경이 생기면 영향받은 기준만 다시 검증한다.

### 모델별 검증

결정론적 프로젝트 검사와 제품 결과 계약은 모델과 무관하게 유지한다. 공통 스킬은 활성 호스트의 참조 하나만 읽으며, 모델이 생성하는 자기검토와 검증 위임만 다음처럼 구분한다.

- Codex는 `references/codex-cli.md`, Claude Code는 `references/claude-code.md`만 읽고, 모델별 검토 정책은 그 참조가 원본이다.
- Gemini와 그 밖의 호스트는 공통 검증 정책만 사용한다.
- 호스트 참조에 절이 없는 모델은 공통 정책과 호스트 공통 지침만 사용한다. 새 모델이 나왔다는 이유만으로 절을 추가하거나 측정하지 않는다.
- 모델을 주력으로 채택하거나 이상 행동을 관측했을 때 현재 하네스와 축소 하네스를 대표 작업에서 비교한다. 공통 정책만으로 검토 결정이 달라질 때만 모델 절을 두고, 측정된 이득이 없는 모델 전용 지시는 제거한다.

### Model Fit

사용자가 모델 선택이나 비교를 요청할 때만 Brief 이후 `references/model-fit.md`로 실행 모델을 권고한다. 후보 정보, 판단 순서, 결과 기록은 그 참조가 원본이다. 권고는 전환 권한이 아니며 수용 조건·테스트·빌드 증거를 대체하지 않는다.

발동 조건을 사용자 요청으로 좁힌 근거는 ADR 0005에 있다.

### 교차 호스트 결과 계약

Codex와 Claude Code에 같은 내부 도구 순서를 강제하지 않는다. 다음 결과만 동일하게 평가한다.

- 요청 의도에 맞는 `direct / plan / lean` 경로
- 제품 원본 재사용과 Brief 생성 결정
- 구현 권한과 파일 변경 권한 준수
- 질문, 수용 조건, 결정, 남은 위험
- 서브에이전트 사용 근거와 결정론적 검증 증거

공급자별 실행기는 동일 사례와 JSON 결과 스키마를 사용하고 모델·effort, 입력·출력·reasoning 또는 thinking 토큰, 캐시 읽기·쓰기, 지연, 비용을 가능한 범위에서 정규화한다. 공급자마다 입력과 캐시 토큰의 원시 의미가 다를 수 있으므로 서로 합쳐 직접 비교하지 않는다. `--require-all`은 Codex와 Claude의 모든 등록 사례가 있을 때만 성공한다. 기본 저장소 검사는 정상 fixture와 빈 결과·단일 공급자·중복·미등록·잘못된 구조 같은 부정 사례로 계약을 검증하고 실제 모델 호출은 명시적인 eval 실행에서만 수행한다.

### 외부 프레임워크와 스킬

설치 여부만으로 호출하지 않는다. 현재 작업에 필요한 특화 능력과 추가되는 문맥·게이트 비용을 비교한다. 공급자 실패를 고치기 위해 사용자 작업을 중단하지 않고 내장 절차로 돌아간다.

### 기억과 검색

유사도 기반 과거 대화를 자동 주입하지 않는다. Brief와 명시적 프로젝트 결정만 기본 기억으로 사용한다. 문서 전체가 문맥에 들어오면 전체를 우선하고, 너무 큰 자료에만 검색·RAG를 사용하며 원칙과 예외의 연결을 복원한다.

### 도구 사용

“최신이라는 단어가 있으면 검색” 같은 키워드 규칙을 만들지 않는다. 최신성, 계산, 외부 상태, 불확실성, 부작용을 기준으로 모델이 도구를 선택한다.

## 검증 경계

다음은 계속 강제한다.

- 프로젝트가 정한 테스트·정적 검사·빌드
- 스키마, 형식, 필수 항목, 계산 결과
- 보안·권한·데이터 무결성
- 비가역 행동과 외부 상태 변경 전 사용자 권한
- 변경 후 실제 명령 결과와 실패 공개

검증 도구의 통과가 제품 품질 전체를 보장한다고 표현하지 않는다. 각 증거가 무엇을 증명하는지 Brief에 분리해 기록한다.

## 호환성

- 감사형 10단계 상태 머신과 `dotagents-workflow` 명령은 두지 않는다. 마지막 구현과 설계는 ADR 0005가 가리키는 Git 이력에서 추적한다.
- 기존 제품 원본이 충분한 lean 경로는 fallback Brief 템플릿을 읽지 않는다.
- 호스트별 검증 참조는 서로 배타적으로 로드한다.
- 외부 공급자 스킬은 레지스트리에 검토 목록으로 남기고, lean에서 현재 작업에 필요한 능력만 개별 호출한다.

## 성공 기준

- 스킬 설명과 사용서가 기획 전용 `plan`과 구현용 `Brief → Execute → Verify`를 구분한다.
- Brief template이 기존 권위 원본 재사용과 로컬 fallback을 구분하고 `AC-<번호>`를 실행·검증까지 연결한다.
- Codex와 Claude Code가 공통 결과 계약과 각자의 검증 참조 하나만 사용한다.
- 같은 eval 사례와 결과 스키마가 두 공급자의 행동과 비용을 비교할 수 있다.
- Model Fit reference가 사용자 요청 시 하드 제약, 대표 eval, 문맥 연속성, 품질 기준 후 비용·지연 최적화를 같은 순서로 적용한다.
- Model Fit 권고와 호스트의 실제 전환 권한이 분리되고, Claude·Codex 우선 지원과 로컬 후보 확장점이 문서화된다.
