## Problem Statement

dotagents already has a home for shared rules, skills, hooks, external integrations, and host adapters, but it does not yet provide an executable way to start, resume, and verify the product-development process defined by the user. The goal is to make the following ten stages reusable across Claude Code, Codex, and Gemini:

1. Grill-me interview
2. Domain document
3. gstack office hours
4. Light spec
5. Plan
6. Plan review
7. Subagent implementation
8. Code and test review
9. Architecture improvement
10. Skill refactoring (optional)

The workflow must neither copy external skills unconditionally nor depend on one host's command syntax. It should use installed external skills when available and continue with built-in procedures that satisfy the same artifact contract when they are absent.

## What Makes This Cool

The important outcome is not a collection of good prompts. It is a durable chain of project-local state from idea to an implementation with recorded verification evidence. Every stage consumes the relevant chain of approved artifacts, so a different session, agent, or host can resume from the same point.

## Constraints

- Human-edited sources remain under `agents/`.
- No new root-level `skills/`, `hooks/`, or `workflows/` directories.
- Human-facing documentation is written as a Korean original and an English translation. A Korean `README.md` has a `README.en.md` sibling.
- Agent- or machine-consumed files such as `SKILL.md`, `AGENTS.md`, TOML, and runtime state remain single-source.
- Do not store secrets, absolute repository paths, or private project information.
- External skills are optional dependencies. Their absence must not block the workflow.
- This scope ends at local execution and verification. Automatic external-skill downloads, MCP credentials, and deployment are excluded.
- Runtime state must not be written into the shared `.agents` source link.

## Premises

### Premise 1: Every task should run all ten stages

False. The image defines the default path for meaningful product-development work. Before startup, the orchestrator classifies the task and confirms applicability with the user:

- `small`: a known, local change with no product or domain decision. Do not start this workflow.
- `standard`: new behavior or unresolved requirements within one bounded area. Use the ten-stage contract.
- `substantial`: multiple surfaces/services/domain boundaries or an architectural decision. Use the contract with stronger plan review.

The CLI accepts only `standard` or `substantial`, recording `--scope` in state. Stage 10 remains optional at startup.

### Premise 2: External skill names are the workflow contract

False. `grilling`, gstack, and Superpowers are providers. The contract consists of inputs, artifacts, and approval conditions. Provider names and installation paths may change without changing the contract.

### Premise 3: Markdown alone is enough for resumption and completion checks

Insufficient. Markdown is readable, but it does not reliably expose the current stage, approval state, or missing artifacts. A minimal state tool is required.

### Premise 4: A full workflow engine is required

Excessive. The AI creates content and judgments. A deterministic tool only needs to validate state transitions and artifact existence, so a small shell-based state manager is enough.

## Approaches Considered

### Approach A: Declarative contract + orchestrator skill + small state tool

Declare stages in `workflow.toml`, provide host-neutral execution rules in one `SKILL.md`, and let a small CLI handle start, status, approval, and completion checks. Each host links to the same skill source.

- Benefits: host-neutral, resumable, testable, external providers are replaceable
- Cost: define a state format and extend installer tests

### Approach B: Markdown playbook only

Put all ten stages and prompts in one document and rely on manual progress.

- Benefit: smallest implementation
- Drawbacks: no reliable resumption, approval gates, omission checks, or host installation

### Approach C: Full CLI state machine

Let the CLI control stage execution and external tool calls.

- Benefit: more automation
- Drawbacks: tight coupling to host syntax and external-skill versions, much larger maintenance surface

## Recommended Approach

Choose Approach A. Keep workflow semantics in a declarative contract, conversation and judgment in the orchestrator skill, and machine-verifiable state in the CLI. This is the minimum useful boundary for turning dotagents from an asset collection into a reusable final operating setup.

## Design

### Source and installation layout

```text
agents/workflows/product-development/
├── WORKFLOW.md
├── WORKFLOW.en.md
└── workflow.toml

agents/skills/owned/product-development-workflow/
├── SKILL.md
├── agents/openai.yaml
└── references/
    ├── stages.md
    └── artifacts.md

tooling/scripts/workflow.sh
tooling/tests/workflow_test.sh
```

Host discovery paths are fixed from official documentation and local behavior as of 2026-08-02:

| Host | User scope | Project scope | Delivery |
|---|---|---|---|
| Claude Code | `~/.claude/skills/<name>` | `.claude/skills/<name>` | installer-manifest link to the source skill |
| Codex | `~/.agents/skills/<name>` | `.agents/skills/<name>` | existing `.agents` link plus `agents/skills/<name>` discovery alias |
| Gemini CLI | `~/.agents/skills/<name>` or `~/.gemini/skills/<name>` | `.agents/skills/<name>` or `.gemini/skills/<name>` | reuse the same `.agents` alias as Codex |

The source always remains in `agents/skills/owned/product-development-workflow/`; `agents/skills/product-development-workflow` is only a relative discovery symlink. Project installation links the CLI to `<project>/.dotagents/bin/dotagents-workflow`; global installation links it to `~/.local/bin/dotagents-workflow`. If `~/.local/bin` is absent from `PATH`, installation succeeds but prints an actionable warning and direct command path.

### Runtime storage

```text
<project>/.dotagents/runs/<run-id>/state
<project>/docs/workflows/<run-id>/
├── 01-interview.md
├── 01-interview.en.md
├── ...
└── 10-skill-retro.en.md
```

`.dotagents/runs/` is local runtime state. In a Git repository, `--project` must equal the physical path from `git rev-parse --show-toplevel`; otherwise the command stops and reports the correct project root. `start` adds `/.dotagents/runs/` once to the local exclude file resolved by `git rev-parse --git-path info/exclude`; it does not edit repository `.gitignore`. Artifacts under `docs/workflows/` are committable evidence for team review and resumption. A run ID permits only lowercase alphanumerics and hyphens to prevent path traversal.

### State model

The state file uses a constrained, non-executable `key=value` format. Exactly thirty-seven fixed keys appear once, values are allow-listed strings, numbers, UTC timestamps, or SHA-256 digests, and the file is never sourced. This single file is authoritative for both execution and approval state.

- `state_version`
- `run_id`
- `scope`: `standard` or `substantial`
- `current_stage`
- `approved_through`
- `status`: `active` or `completed`
- `optional_skill_refactor`: `yes` or `no`
- `approval_01_at` ... `approval_10_at`: `-` before approval, then `YYYY-MM-DDTHH:MM:SSZ`
- `artifact_01_ko_sha256`, `artifact_01_en_sha256` ... `artifact_10_ko_sha256`, `artifact_10_en_sha256`: `-` before approval, then the SHA-256 of the exact files the user approved

The CLI exposes only:

```text
dotagents-workflow start --project PATH --run RUN_ID --scope standard|substantial [--skip-skill-refactor]
dotagents-workflow status --project PATH --run RUN_ID
dotagents-workflow approve --project PATH --run RUN_ID --stage N --user-approved
dotagents-workflow adopt --project PATH --run RUN_ID --scope standard|substantial --through N --user-approved [--skip-skill-refactor]
dotagents-workflow verify --project PATH --run RUN_ID
```

`start` creates state and directories and then prints the same ten-stage list as `status`; it does not create artifact content. The orchestrator may call `approve --user-approved` only after explicit user confirmation. The CLI structurally checks that both Korean and English artifacts for the current stage are non-empty regular files, are not symbolic links, and live directly under the canonical artifact directory, then writes the approval UTC time and both SHA-256 digests to the single state file. Later `status`, `approve`, and `verify` calls recheck every approved digest and reject changed approval evidence. Semantic translation equivalence and artifact quality remain an orchestrator-and-user review, not a CLI guarantee.

`adopt` imports existing interviews, specs, or plans after they have been **copied** to canonical artifact names. External and symbolic links are rejected for portability and path safety. `N` is 1–10, and state plus approval hashes are created only if every pair from stage 1 through `N` is a regular file and the user approves the set. For `N < 9`, the result is current `N+1`, approved `N`, active. At `N=9`, stage 10 enabled means current 10, approved 9, active; stage 10 skipped means the same numbers and completed. `N=10` is allowed only with stage 10 enabled and ends at current 10, approved 10, completed. `--through 10 --skip-skill-refactor` is rejected. If artifacts exist without state, or only an empty run-state directory remains after the state file is lost, `start` fails and `adopt` can recover it. A directory containing a real state file or another runtime file is never overwritten.

`verify` is **workflow structure and integrity verification**: it checks that every required pair is a regular non-symlink file directly under the canonical artifact directory, approval timestamps and hashes are continuous, current files match the approved hashes, and completion state is correct. It does not independently prove implementation correctness or successful tests; evidence for those claims is required in stages 7–9 and covered by user approval.

### Declarative contract schema

`workflow.toml` uses a restricted line-oriented TOML profile so it can be parsed without adding a dependency. The top level contains `schema_version`, `id`, and `state_version` exactly once. Every `[[stages]]` block contains the following keys exactly once and in order:

```toml
schema_version = 1
id = "product-development"
state_version = 1

[[stages]]
number = 1
id = "interview"
title_ko = "그릴미 인터뷰"
title_en = "Grill-me interview"
artifact = "01-interview"
optional = false
predecessor = 0
requires_approval = true
```

Strings are quoted ASCII IDs/artifact basenames or UTF-8 titles, `optional` is `true|false`, and numbers are 0–10. In version 1, `requires_approval` must be `true` for every stage. Stages are contiguous 1–10, `predecessor = number - 1`, and only stage 10 is optional. An `awk` parser in `workflow.sh` turns this restricted profile into TSV and rejects unknown keys, order, duplicates, and unsupported versions. `status`, `approve`, `adopt`, `verify`, and tests read stage names, artifacts, and optionality from that TSV; no second stage table is hard-coded in shell.

### State invariants and transitions

- Active state satisfies `current_stage = approved_through + 1` and `status = active`.
- Initial state is stage 1, approved through 0, with every approval timestamp and artifact hash set to `-`.
- Only the current stage can be approved; reapproval, reverse approval, and arbitrary skipping fail.
- With stage 10 enabled, its approval ends at current 10, approved 10, completed.
- With stage 10 disabled, stage 9 approval ends at current 10, approved 9, completed.
- Completed state rejects further approval.
- Unsupported state versions fail without mutation and request an upgrade.
- A mutating command first writes a complete temporary owner file in the state root with four lines: `pid=<digits>`, `created_at=<Unix epoch>`, `process_started=<ps -p PID -o lstart= value>`, and `token=<random token>`. It then atomically acquires `.dotagents/runs/.<run-id>.lock` with `mkdir` and publishes the complete owner through a non-overwriting hard link. A competing process treats an ownerless directory younger than five seconds as live initialization and reclaims only an ownerless directory older than five seconds. A stale lock is atomically moved to a unique quarantine path before removal. If the original process resumes after reclamation, it cannot overwrite a newly published owner. Normal/signal cleanup, the moment before a state write, and release all revalidate that the owner token belongs to the current command. Ownership requires `kill -0 PID` plus an exact recorded process start time when available, avoiding Bash process-name ambiguity and PID reuse. If a sandbox forbids `ps` and records `process_started=unavailable`, a live PID is never reclaimed based on age alone; the command fails closed. Tests cover ownerless initialization, dead owners, PID reuse shape, an old live owner, and real concurrent approval.
- State mutation writes a complete temporary file in the same directory and atomically `mv`s the single authoritative state file. Readers fail on a live lock and reclaim a stale lock before reading. Approved artifacts are immutable evidence; a hash mismatch blocks both reads and later mutations.
- The project root is physically canonicalized; symlinked state/artifact roots or run directories are rejected.
- Exit 0 means success, 2 means usage/input error, and 3 means contract/state/artifact validation failure. Human-readable output uses `key: value` lines.

### Stage contract

| Stage | Default execution | Approved artifacts |
|---|---|---|
| 1. Interview | Use `grilling`/`grill-me` when installed; otherwise ask one built-in question at a time | `01-interview.md`, `.en.md` |
| 2. Domain | Actors, language, entities, commands/events, invariants, boundaries, non-goals | `02-domain.md`, `.en.md` |
| 3. Office hours | Use gstack `office-hours`; otherwise challenge premises and compare 2–3 approaches | `03-design.md`, `.en.md` |
| 4. Light spec | Goals, non-goals, user stories, acceptance criteria, constraints, open questions | `04-spec.md`, `.en.md` |
| 5. Plan | Prefer Superpowers `writing-plans`; include exact files, tasks, and test commands | `05-plan.md`, `.en.md` |
| 6. Plan review | gstack `autoplan` or a suitable CEO/design/engineering review sequence | `06-plan-review.md`, `.en.md` |
| 7. Implementation | Fresh subagent per task when possible, TDD, spec compliance before quality review | `07-implementation.md`, `.en.md` |
| 8. Code/test review | Project checks, code review, product-appropriate QA, then rerun checks | `08-review.md`, `.en.md` |
| 9. Architecture assessment/improvement | Assess coupling, cohesion, duplication, and boundaries; change only with evidence and user approval, then rerun all stage 8 checks | `09-architecture.md`, `.en.md` |
| 10. Skill-refactoring candidate | Report repeated successful procedures and candidates; create a skill only under separately authorized write scope; optional at startup | `10-skill-retro.md`, `.en.md` |

Every stage consumes all approved prior artifacts relevant to its decision, not just the immediately preceding document. In particular, stage 7 reads `04-spec`, `05-plan`, and `06-plan-review`; a conflict follows the latest explicit user-approved decision. Agents look up discoverable facts in the repository or official documentation rather than asking the user. Product decisions require user approval. Korean and English artifacts must be semantically equivalent and are approved as one unit. `artifacts.md` requires purpose, inputs, decisions, and open questions at every stage; stages 7–9 additionally require changed files, commands, exit results, remaining failures, and user decisions. Stage 9 cannot be approved after a code change without rerunning and recording every relevant stage 8 check.

### Failure and recovery

- External skill absent: continue with the built-in procedure.
- External skill installed but failing or incompatible: record the failure in the current artifact and retry once with the built-in procedure; do not auto-modify or downgrade the external skill.
- One artifact missing or empty: `approve` fails and reports it.
- Corrupt state or unknown key: stop with validation failure without executing state content.
- Interrupted session: `status` reports the current stage and expected files. If the state file is lost but artifacts and an empty run-state directory remain, review them and recover with `adopt`.
- Repository moved: reinstall only links owned by the existing installation manifest.
- User-file collision: default installation makes no changes; only `--force` backs up the file.

### Routing

Use the orchestrator when the user asks to build a product from the beginning, work from interview through implementation, or invokes the ten-stage workflow explicitly. Do not use it for a single bug, a small edit, an explanation, or research. To begin from an existing spec or plan, copy it into canonical regular artifact files, fill required prior content from the existing material, and use `adopt --through N --user-approved` after the user reviews the set. Do not rerun an interview performatively or approve empty placeholders.

### Documentation language policy

From this change onward, repository-owned human-facing documentation has a Korean default and an English `.en.md` sibling. The user explicitly required `README.en.md` whenever a README is Korean, so all 21 existing human-facing READMEs receive English siblings in this change. Target-project run artifacts also use Korean-English pairs under the user's default policy. Structure tests verify repository README pairs and the workflow-document pair. Agent instructions and machine contracts remain single-source so translations cannot diverge in executable meaning.

## Open Questions

- Whether shipping and PR creation deserve an eleventh stage will be decided from real usage. For now, shipping is an optional next action after the ten stages.
- Distinct run IDs isolate state only. Concurrent implementation runs must use separate branches/worktrees because they can otherwise modify the same worktree.

## Success Criteria

- One command starts a workflow in a new project and reports all ten stages and expected artifacts.
- A stage cannot be approved without its artifact pair, and an interrupted run resumes from the same state.
- The built-in procedure can complete the workflow with no external skills installed.
- Global and project installation create skill paths for all three hosts and pass repeat-install, repository-move, and uninstall tests.
- Human documentation exists in Korean-English pairs with usage examples in both languages.
- `./tooling/scripts/check.sh`, install tests, structure tests, and workflow tests all pass.

## Distribution Plan

Use the existing dotagents installer and its global/project symbolic links. Add no package manager or network download. After checks pass in a GitHub PR and the change is merged, users pull the repository and rerun the installer.

## What I Noticed About How You Think

- “A shared setup or final version I can use across multiple projects” clearly sets the bar above a reference collection: this must be installable and repeatedly executable.
- “Can hooks and skills be grouped into their own folders? There are too many things at the root” became a direct design constraint. New functionality stays within the `agents/` and `tooling/` boundaries.
- The ten-stage image expresses the desired experience concretely; the linked repositories are best treated as proven execution providers, not sources to copy wholesale.
