## 문제

Claude Code와 Codex를 함께 사용할 수 있는 개발자가 제품 워크플로우를 시작할 때, 현재 계약은 이미 활성화된 모델의 검증 방식만 조정하고 작업에 더 적합한 공급자·모델·effort를 판단하지 않는다. 그 결과 사용자는 복잡도·위험·비용·지연·문맥 이전 비용을 매번 임의로 비교하거나, 익숙한 모델을 모든 작업에 사용해 품질 또는 비용을 포기한다.

## 원하는 결과와 성공 신호

- 결과: Brief가 정리된 뒤 실행 전에 사용 가능한 Claude·Codex 후보를 같은 기준으로 비교하고, 현재 모델 유지 또는 정확한 후보로 전환할지를 근거·확신도와 함께 권고한다.
- 성공 신호: 대표 시나리오에서 하드 제약을 먼저 적용하고, 성공 가능성·실제 eval·문맥 연속성·비용과 지연 순으로 판단하며, 후보가 비슷하거나 전환할 수 없을 때 불필요한 중단이나 가짜 자동 전환을 만들지 않는다.

## 판단 원칙

- 고정 모델 매핑보다 실행 시점의 후보 인벤토리를 선택한다. 모델 이름·가격·가용성은 바뀌기 때문이다.
- 숫자 하나의 종합 점수보다 하드 제약과 순서가 있는 증거 판단을 선택한다. 확인되지 않은 품질 차이에 거짓 정밀도를 부여하지 않기 때문이다.
- 새 모델의 추정상 이점보다 현재 문맥 연속성을 기본값으로 선택한다. 공급자 전환에는 문맥 이전·재검증 비용이 있기 때문이다.
- 공급자 설명보다 프로젝트의 대표 작업 eval을 우선한다. 실제 프롬프트·도구·저장소에서의 성공률이 일반 카탈로그보다 직접적인 증거이기 때문이다.
- 모델 권고와 실행 권한을 분리한다. 호스트가 전환을 지원하지 않거나 외부 호출·추가 비용 권한이 없으면 권고만 기록해야 하기 때문이다.
- Claude·Codex 전용 분기보다 공급자 중립 후보 형식을 선택한다. 초기 지원은 두 회사로 제한하되 이후 로컬 LLM을 같은 계약으로 추가할 수 있기 때문이다.

## 절대 제약과 비목표

- 제약: 프로젝트 보안·데이터 정책, 권한, 도구·모달리티·문맥 요구와 예산은 어떤 권고보다 우선한다. 사용자 모델 고정은 그 하드 제약을 통과한 뒤의 선택 제약이며, 충돌하면 해당 모델을 실행하지 않고 방향을 확인한다.
- 제약: 모델 선택을 이유로 유료 benchmark, 외부 공급자 호출, 인증 변경, 새 세션 시작을 자동 수행하지 않는다.
- 제약: 공식 모델 설명은 최신 공식 문서로 확인하고, 모델 업그레이드 시 대표 eval로 정책을 재검증한다.
- 비목표: 이번 변경에서 Claude Code나 Codex 호스트 자체의 모델 전환 API를 구현하지 않는다.
- 비목표: 가격표나 전체 모델 카탈로그를 저장소에 복제하지 않는다.
- 비목표: 로컬 LLM의 구체적 런타임·모델을 초기 지원 목록에 넣지 않는다.
- 비목표: Model Fit을 별도 승인 단계나 고정 멀티모델 체인으로 만들지 않는다.

## 남은 위험
