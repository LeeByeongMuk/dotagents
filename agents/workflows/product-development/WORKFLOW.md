# 제품 개발 워크플로우

제품의 `무엇`과 `왜`를 한 장의 기획 하네스에 고정하고, 실행은 모델에 맡긴 뒤 결정론적 증거로 검증하는 공통 절차입니다. Claude Code, Codex, Gemini에서 기본 경로는 `Brief → Execute → Verify`입니다.

기존 10단계 상태 머신은 삭제하지 않고 감사·규제·고위험 작업을 위한 `audited` 호환 경로로 보존합니다.

## 경로 선택

| 경로 | 사용 조건 | 실행 방식 |
|---|---|---|
| `direct` | 작은 수정, 단일 버그, 설명, 조사 | 프로젝트 일반 구현·검증 절차 |
| `lean` | 이 스킬로 수행하는 일반 제품·기능 개발 | Brief → Execute → Verify |
| `audited` | 명시적 요청, 규제, 민감한 보안 경계, 비가역 마이그레이션, 공식 팀 승인·인수인계 | 보존된 10단계 계약과 단계별 승인 |

파일 수나 작업 규모만으로 `audited`를 선택하지 않습니다. 복잡한 기능도 대부분 `lean`에서 실행하고, 형식적 증거가 필요한 구체적 위험이 있을 때만 단계를 늘립니다.

## 기본 경로

```text
BRIEF                    MODEL FIT(조건부)              EXECUTE                    VERIFY
문제·목적·판단 기준   →   후보·제약·eval 비교       →   모델이 순서·도구·계획 결정   →   수용 조건·테스트·빌드 증거
제약·결정·수용 조건       유지·전환 권고와 근거 기록       필요할 때만 외부 능력 사용       결과와 남은 위험 기록
```

### 1. Brief

Brief는 제품 결정의 권위 있는 원본입니다. 프로젝트의 현재 PRD·이슈·스펙이 이미 그 역할을 한다면 새 문서를 만들지 않고 채택합니다. 적합한 원본이 없을 때만 `docs/workflows/<run-id>/brief.md`를 만들고 작업 내내 갱신합니다. 외부 또는 읽기 전용 원본이라면 로컬 Brief는 원본을 링크하고 실행 체크포인트·검증 증거처럼 원본이 담지 못하는 정보만 기록합니다.

권위 원본과 로컬 실행 기록은 합쳐서 다음 내용을 포함해야 합니다.

- 누가, 언제, 무엇을 하지 못해 무엇을 포기하는지에 대한 문제 정의
- 해결 후 달라지는 결과와 관찰 가능한 성공 신호
- `A보다 B를 선택한다. 왜냐하면 ...` 형식의 판단 원칙
- 보안·비용·일정·호환성 등 절대 제약과 비목표
- 수용 조건
- 결정, 버린 대안, 이유
- 사용자에게 남은 제품 결정
- 재개 체크포인트와 검증 증거

사용자 요청과 저장소에서 이미 확인 가능한 내용을 다시 인터뷰하지 않고, 결과를 바꾸는 제품 정보가 빠져 있을 때만 질문합니다. 중요한 가정·대안·사용자 소유 결정이 결과를 바꿀 수 있을 때만 실행 전에 한 묶음으로 알립니다. 이는 승인 게이트가 아니며, 방향을 막는 열린 결정이 있을 때만 답을 기다립니다. 제품 사실은 채택한 권위 원본에, 실행 체크포인트와 증거는 필요한 경우 로컬 Brief에 기록하고 같은 사실을 복제하지 않습니다.

### 2. Model Fit: 조건부

호스트가 실행 가능한 모델 후보를 둘 이상 제공하거나 사용자가 모델 선택을 요청하면 Brief 이후 한 번 판단합니다. 초기 정책은 Claude와 Codex/OpenAI 계열을 같은 후보 형식으로 비교하며, 공급자·정확한 모델 ID·가용성·공식 역할·effort·도구·문맥·데이터 경계·상대 비용과 지연·프로젝트 eval을 입력으로 사용합니다.

판단 순서는 다음과 같습니다.

1. 인증·가용성·보안·데이터 정책·필수 도구·모달리티·문맥·예산 같은 하드 제약을 적용합니다.
2. 작업 성공 위험과 대표 프로젝트 eval을 우선합니다.
3. 후보가 비슷하면 현재 문맥을 유지합니다.
4. 품질 기준을 만족한 후보 사이에서만 비용과 지연을 최적화합니다.

숫자 하나의 종합 점수나 키워드별 모델 표를 만들지 않습니다. 결과에는 정확한 모델·effort, 유지 또는 전환 권고, 확신도, 근거, 가장 강한 대안, 실행 가능 여부와 재평가 조건을 기록합니다. 권고는 모델 전환 권한이 아닙니다. 호스트가 전환을 지원하지 않거나 외부 호출 권한이 없으면 현재 모델로 계속하고 다음 실행 권고만 남깁니다. 유료 benchmark나 고정된 두 모델 토론은 자동 실행하지 않습니다.

세부 계약은 스킬의 `references/model-fit.md`에 있습니다. 로컬 LLM은 같은 후보 메타데이터와 대표 eval을 제공할 수 있을 때 이후 확장할 수 있습니다.

### 3. Execute

주 에이전트가 Brief와 전체 문맥을 바탕으로 계획·순서·도구를 자율적으로 선택합니다.

- 외부 스킬은 정해진 체인으로 호출하지 않고 현재 작업에 특화된 능력이 필요할 때만 사용합니다.
- 멀티에이전트는 진짜 병렬 작업, 문맥 격리, 전문 도구, 독립적인 고위험 검토에만 사용합니다.
- 기획자 → 작성자 → 검토자처럼 역할만 나누지 않습니다.
- 문맥이 모델 입력 범위에 들어오면 원문 전체를 우선 사용합니다. 검색·RAG는 너무 큰 자료에만 쓰고 원칙과 예외의 관계를 보존합니다.
- 유사도 기반 기억을 자동 주입하지 않고 Brief의 명시적 결정 기록을 읽습니다.
- 도구 사용은 키워드가 아니라 불확실성, 최신성, 계산 필요, 부작용 위험으로 판단합니다.
- 되돌릴 수 있는 기술 선택은 자율적으로 처리하고, 제품 방향이나 비가역 행동만 사용자에게 확인합니다.

### 4. Verify

Brief의 모든 수용 조건과 프로젝트가 정한 검사를 실제로 실행합니다.

- 관련 테스트, 정적 검사, 빌드, 스키마·형식 검사
- 제품 종류에 맞는 핵심 사용자 흐름과 실패 상태
- 보안·데이터·마이그레이션처럼 diff가 드러내는 위험에 대한 표적 검토
- 실패 수정 후 영향받은 검사의 재실행
- 변경이 도메인 규칙, 공개 인터페이스, 연동 지점을 바꿨다면 완료 전에 영향받은 컨텍스트 문서 갱신

“전체적으로 잘됐는지 반복 검토”처럼 종료 조건이 모호한 루프나 고정된 모델 자기검토 단계를 사용하지 않습니다. 빈칸, 형식, 계산, 테스트, 수용 조건처럼 참·거짓을 판별할 수 있는 증거를 우선합니다. 결과와 남은 위험은 채택한 원본의 실행 기록 또는 로컬 Brief에 기록합니다.

모델이 생성하는 검토는 현재 모델에 맞춥니다. Claude Opus 5에는 별도 최종 자기검토나 검증 서브에이전트를 기본 추가하지 않습니다. Claude Fable 5는 장기 실행에서만 도구 결과로 진행 주장을 확인하고, 결과를 바꿀 수 있는 스펙·위험 체크포인트에 fresh-context 검증자를 선택적으로 사용합니다. GPT-5.6 Sol은 반복 자기검토 없이 구체적 diff 위험만 표적 검토합니다. 세부 계약과 공식 근거는 스킬의 `references/model-verification.md`에 있습니다.

Model Fit은 실행 모델을 고르는 정책이고 모델별 검증은 실제 활성 모델로 검증하는 정책입니다. 모델 권고 자체를 구현 정확성의 증거로 사용하지 않습니다.

## 사용

```text
$product-development-workflow 로 이 제품 아이디어를 Brief부터 구현 검증까지 진행해줘.
```

에이전트는 기본적으로 `lean`을 선택합니다. 별도 상태 CLI는 필요하지 않습니다. 중단 후에는 채택한 제품 원본, 로컬 Brief가 있으면 그 파일, Git 상태, diff, 최근 커밋을 읽고 체크포인트부터 이어갑니다.

## 감사형 10단계 경로

다음처럼 명시적으로 요청하거나 형식적 승인 증거가 필요할 때만 사용합니다.

```text
$product-development-workflow 의 audited 경로로 이 마이그레이션을 진행해줘.
```

`audited` 경로는 다음 순서를 유지합니다.

```text
인터뷰 → 도메인 → 설계 → 스펙 → 플랜 → 플랜 리뷰
→ 구현 → 코드·테스트 리뷰 → 아키텍처 평가 → 스킬 회고(선택)
```

이 경로의 기계 계약은 [workflow.toml](workflow.toml), 상세 실행·산출물 규칙은 스킬의 `references/stages.md`와 `references/artifacts.md`입니다.

### 시작과 상태

```bash
dotagents-workflow start \
  --project /path/to/project \
  --run checkout-redesign \
  --scope substantial

dotagents-workflow status \
  --project /path/to/project \
  --run checkout-redesign
```

감사 산출물은 `<project>/docs/workflows/<run-id>/01-interview.md`부터 단계별로 생성됩니다. 에이전트가 산출물을 보여주고 사용자의 명시적 승인을 받은 뒤에만 승인 명령을 호출합니다.

```bash
dotagents-workflow approve \
  --project /path/to/project \
  --run checkout-redesign \
  --stage 1 \
  --user-approved
```

승인된 감사 산출물은 SHA-256으로 고정됩니다. 일반 `lean` Brief에는 이 불변 정책을 적용하지 않습니다.

### 가져오기와 완료 검증

```bash
dotagents-workflow adopt \
  --project /path/to/project \
  --run existing-plan \
  --scope standard \
  --through 5 \
  --user-approved

dotagents-workflow verify \
  --project /path/to/project \
  --run checkout-redesign
```

CLI 검증은 단계 순서, 파일 안전성, 승인과 해시의 연속성만 증명합니다. 구현 정확성은 7~9단계에 기록된 실제 테스트·QA 결과가 증명해야 합니다.

## 외부 스킬

`grilling`, gstack, Superpowers는 선택 공급자입니다. `lean`에서는 필요한 능력만 개별 호출하고, `audited`에서는 지정 단계의 공급자로 사용할 수 있습니다. 설치되지 않았거나 현재 계약과 맞지 않으면 외부 스킬을 고치거나 설치하지 않고 내장 절차를 사용합니다.

## 실패와 복구

- `lean` 중단: 같은 Brief와 Git 상태에서 재개합니다.
- `lean` 결정 변경: Brief의 현재 결론을 수정하고 결정 기록에 이유를 남깁니다.
- `lean`에서 `audited`로 전환: 같은 run-id의 산출물 디렉터리가 이미 있어 `start`가 거부됩니다. 새 run-id로 시작하거나, 같은 run-id를 유지하려면 Brief를 바탕으로 필요한 정규 단계 산출물을 작성하고 사용자 검토 후 `adopt`합니다.
- `audited` 중단: `dotagents-workflow status`로 재개합니다.
- `audited` 상태 손실: 기존 정규 산출물을 검토한 뒤 `adopt`합니다.
- 외부 공급자 실패: 원인을 간단히 기록하고 내장 절차로 한 번 계속합니다.
- 검증 실패: 원인을 해결하고 영향받은 검사를 다시 실행합니다.

배포, 푸시, PR 생성은 사용자 요청이 있을 때 수행하는 후속 행동이며 암묵적 추가 단계가 아닙니다.

프로젝트를 넘어 재사용할 만한 관례를 발견했다면 완료 보고에 dotagents 승격 후보로만 제안합니다. 실제 반영은 별도 승인 뒤 `dotagents-promote` 스킬이 격리된 worktree 브랜치에서 수행하며, main 반영은 사용자의 머지로 확정됩니다.
